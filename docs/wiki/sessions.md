# Сессии (SQLite)

Код: [`agent/store.py`](../../agent/store.py). Тесты: [`tests/test_store.py`](../../tests/test_store.py).

Сессия — это диалог с агентом: история сообщений, рабочая папка, модель и разрешения «всегда».
Хранится в SQLite (stdlib `sqlite3`, режим WAL — читатели не блокируют писателя).

| Где | Файл | Владелец сессии (`owner`) |
|---|---|---|
| Сервер | `DB_PATH` шлюза (`data/gateway.db`) — та же база, что и токены | id токена (строкой) |
| CLI | `sessions.db` из настроек (`~/.gwagent/sessions.db`) | `local` |

## Схема

```sql
agent_sessions (
  id TEXT PRIMARY KEY,          -- 16 hex-символов, secrets.token_hex(8)
  owner TEXT,                   -- кому принадлежит; чужую сессию API не показывает
  title TEXT,                   -- по умолчанию — начало первого сообщения
  profile TEXT,                 -- профиль настроек (сервер)
  model TEXT,
  workspace TEXT,               -- абсолютный путь рабочей папки
  allow_rules TEXT,             -- JSON-массив правил, добавленных ответом «всегда»
  created REAL, updated REAL    -- unix time
)
agent_messages (
  session_id → agent_sessions.id ON DELETE CASCADE,
  seq INTEGER,                  -- 1, 2, 3… внутри сессии
  role TEXT,                    -- user | assistant | tool
  data TEXT,                    -- сообщение целиком, JSON в формате OpenAI
  ts REAL
)
agent_tool_runs (               -- журнал аудита вызовов инструментов
  session_id, call_id, tool,
  args TEXT,                    -- JSON аргументов (после правки хуком)
  decision TEXT,                -- allow | deny | ask:allow | ask:deny | error (вызов не дошёл до прав)
  ok INTEGER, ms INTEGER, ts REAL
)
agent_meta (key, value)         -- schema_version
```

Системный промпт в истории **не хранится** — он собирается заново при каждом запуске из
текущих настроек (иначе смена промпта не действовала бы на старые сессии).

### Что лежит в `data`

```json
{"role": "user", "content": "создай hello.txt"}
{"role": "assistant", "content": "Создаю файл.", "tool_calls": [
  {"id": "call_1", "type": "function", "function": {"name": "write_file", "arguments": "{\"path\":\"hello.txt\",\"content\":\"hi\"}"}}]}
{"role": "tool", "tool_call_id": "call_1", "content": "Записано 2 байт в hello.txt"}
{"role": "assistant", "content": "Готово."}
```

Инвариант: за каждым `assistant` с `tool_calls` идут `tool`-сообщения на **все** его `id`.
Агент поддерживает его и при ошибках/отмене (недошедшие вызовы получают результат
«Отменено»), иначе апстрим отклонит историю при продолжении сессии.

## Миграции

Версия схемы — в таблице `agent_meta` (`schema_version`), **не** в `PRAGMA user_version`:
на сервере база общая с токенами шлюза. При открытии `SessionStore` применяет недостающие
миграции из словаря `MIGRATIONS` по порядку, каждую в своей транзакции. Новая миграция:
добавить `MIGRATIONS[N]`, поднять `SCHEMA_VERSION`, дописать тест и этот раздел.

## API класса

| Метод | Что делает |
|---|---|
| `create(owner, title=, profile=, model=, workspace=)` | новая сессия |
| `get(id, owner=None)` | сессия; с `owner` — только своя |
| `find(prefix, owner=None)` | по однозначному префиксу id (`/resume 3fa2`) |
| `list(owner, limit=50)` | свежие сверху |
| `update(id, title=, model=, workspace=, allow_rules=)` | правка полей, обновляет `updated` |
| `delete(id)` | вместе с сообщениями и журналом |
| `add_message(id, message)` / `messages(id)` | история |
| `record_tool(...)` / `tool_runs(id)` | журнал вызовов |

## Где смотреть руками

```bash
sqlite3 data/gateway.db "SELECT id, owner, title, datetime(updated,'unixepoch') FROM agent_sessions"
sqlite3 data/gateway.db "SELECT tool, decision, ok, ms FROM agent_tool_runs WHERE session_id='…'"
```


## Провайдеры локального CLI

CLI использует существующее поле `profile` со значением `provider:NAME` для привязки к
[провайдеру](providers.md); миграция SQLite не требуется. Модель остаётся исходным ID API.
При возобновлении выбирается сохранённое подключение; смена провайдера создаёт новую сессию.
Профили серверного API продолжают иметь прежнее значение.

## Версия схемы 2, восстановление и приватность

Миграция добавляет connection_id, endpoint_hash, summary, context_seq и таблицу agent_turns
со статусами выполнения. Существующие сообщения и токены не удаляются. Старые сессии с пустой
идентичностью подключения совместимы; новые проверяют ID и адрес провайдера.
Каждый ход отмечается running, при завершении сохраняется причина; при возобновлении
незавершённый ход становится interrupted. Незакрытые вызовы получают один результат
«прервано»/«отменено» без повторного исполнения действия. Отмена и закрытие генератора
используют тот же механизм; уже сохранённый результат не дублируется.

Компактация сохраняет checkpoint (summary/context_seq), не удаляя исходные сообщения.
Она работает и после единственного хода: законченный ответ переносится в выдержки,
во время цикла остаётся последняя целая группа вызовов и результатов инструментов.
context_messages восстанавливает пользовательскую реплику перед сохранённой группой,
даже если она находится до context_seq. Повторное сжатие продвигает границу только вперёд
и ограничивает выдержки; последние выдержки прежнего checkpoint также сохраняются.
Исходная цель и последний настоящий запрос дополнительно закрепляются сборщиком контекста. Экспорт содержит полную
историю и журнал инструментов; удаление сессии каскадно удаляет также ходы.
SQLite-файл открывается с 0600, новые каталоги с 0700, симлинк вместо файла запрещён.
Операции execute/fetch и транзакции сериализуются RLock на соединение; close вызывается
в жизненном цикле CLI/сервиса. TokenStore использует тот же механизм.
Ранее нестабильный сбой чтения воспроизведён на исходном TokenStore под 24 потоками
(None вместо токена и InterfaceError); регрессия выполняет параллельные чтения/записи.

## Журнал корреляции (миграция 3)

Версия 3 добавляет к `agent_tool_runs` поля `request_id`, `span_id`, а также таблицу
`agent_trace_events`: `seq`, `request_id`, `span_id`, `parent_span_id`, `session_id`,
`event`, `ts`, `data` (JSON). Индексы по request/session ускоряют выборку.
Старые записи сохраняются; их новые поля идентификаторов пусты.

Журнал содержит начала/окончания запросов, моделей, инструментов и хуков, состояние,
HTTP-статус, токены, длительности, решение прав, модель и connection_id, ссылки на seq сообщений.
Отмена тоже завершает записи span. Отдельные детальные сообщения и аргументы инструментов
остаются в прежних таблицах; журнал метаданных не дублирует текст и секреты.
`SessionStore.traces(session_id, request_id=None)` возвращает связанные root-request записи,
включая дочерние сессии. `export` включает `traces`. Удаление сессии удаляет её trace-строки
через FK; дочерние сессии имеют собственную историю и удаляются отдельно.

Просмотр: `/logs` либо `/logs REQUEST_ID`. Для статистики можно группировать
`model.end` по `data.model`/request_id и суммировать `prompt_tokens`, `completion_tokens`, `ms`;
`tool.end` содержит инструмент и состояние. Python logger `gwagent.trace` также выдаёт JSON
на уровне INFO для подключения стандартных обработчиков логов. CLI хранит аудит в своей SQLite,
сервер — в общей gateway.db, независимо от настройки обработчиков logging.

`workspace_in_use` проверяет оставшиеся ссылки сессий перед серверным удалением общей папки.

## Контрольные точки и редактирование истории (миграция 4)

`agent/checkpoints.py` реализует локальные снимки без Git и дополнительных библиотек.
`agent_checkpoints` связывает request_id с предыдущим запросом активной ветки (`parent_request_id`)
и деревьями до/после. Дерево содержит пути, типы, режимы доступа и SHA-256 объектов файлов;
содержимое хранится с zlib-сжатием в `agent_snapshot_blobs`, повторяющиеся версии не дублируются.
`agent_snapshot_refs` учитывает ссылки объектов. При удалении сессии удаляются неиспользуемые объекты.
Рабочая `.git` не изменяется. Снимки находятся в той же приватной SQLite (0600), что и история.

`agent_message_meta` связывает seq сообщения с request_id, исходным пользовательским текстом
до добавления контекста хуков и метриками ответа. Эти поля не отправляются провайдеру.
`timeline()` возвращает сообщения с метаданными, `revision()` обнаруживает устаревший выбор меню.
`rewind()` удаляет выбранное пользовательское сообщение и последующую активную историю;
прежняя ветка сохраняется в `agent_reverts`, доступна в `/export`. Summary/context_seq сбрасываются.
После повторной отправки создаётся новый request_id и новая ветка контрольных точек.
Детальные записи аудита старой ветки сохраняются.

Режим с файлами применяет обратные изменения всех запросов начиная с выбранного. До записи
проверяются все затронутые пути: текущее состояние должно совпасть с ожидаемым состоянием после
модели; конфликт прерывает откат. Ручные файлы, созданные позднее, не удаляются вместе с папкой.
Выполняются блокировки, проверка симлинков родителей и SHA-256 объектов. Во время активного
запроса в общей workspace откат файлов запрещён. Изменение только сообщения не затрагивает файлы.

Один снимок ограничен 5000 записями и 32 МиБ содержимого. Исключаются `.git`, node_modules,
venv/.venv, __pycache__, .pytest_cache, .mypy_cache, .cache, защищённые креды и сама БД с WAL/SHM.
Сохраняются обычные/двоичные файлы, права, папки и ссылки. Недоступный, слишком большой или
неполный снимок отключает файловый откат для соответствующей истории. Для старых сообщений
без снимков доступен режим редактирования сообщения. Внешние HTTP/MCP-эффекты, изменения
вне workspace и Git-метаданных откатом не отменяются. Снимки фиксируют состояние workspace
во время запроса; параллельную ручную работу с теми же файлами лучше завершить перед запуском агента.

## Автоматические названия

Каждая новая сессия сразу получает имя `Новая сессия · HH:MM · ID`; пустые старые названия
заполняются миграцией. После первой задачи локальный генератор `task_title` создаёт краткое
название по первой содержательной строке (без Markdown-префиксов, до 10 слов/64 символов).
Это не требует модели или дополнительного API-вызова. `title_auto` отличает автоматическое
название от явно заданного серверным клиентом. Явные названия сохраняются; при полном
откате автоматическое имя сбрасывается и генерируется заново по отредактированной задаче.

## Цель и список задач без миграции

`planning_state(session_id)` читает метаданные `planning` успешных tool-сообщений текущей
ветки, восстанавливая goal/todos. Исходная цель до явной замены — первый пользовательский
запрос. Метаданные входят в timeline/экспорт; сжатие не удаляет их, `/revert` удаляет из
активной ветки вместе с сообщениями. Отдельных таблиц и версии схемы не добавлено.
Подробнее — [планирование](tools/planning.md).

## Версия схемы 5 — активный агент

Миграция добавляет agent_sessions.agent_mode с умолчанием build. Старые сессии/сообщения
сохраняются, PRAGMA user_version не используется. Session.to_dict/export включают agent_mode;
допустимы build и plan. Смена сохраняется через SessionStore.update без создания новой сессии.
В метаданных новых сообщений режим фиксируется отдельно, чтобы правильно подписывать
старые ответы после переключения. /revert сохраняет выбранный текущий режим.

## Версия схемы 6 — очередь уточнений

agent_inputs хранит уникальный id, session_id, исходный request_id, text, created, статус
и монотонный seq. pending_inputs возвращает FIFO. enqueue_input выполняется транзакционно,
повтор того же id/запроса/текста не дублирует запись. Лимиты: 32 ожидающих сообщения,
65536 UTF-8 байт на сообщение, 262144 байта суммарно. Значения секретов маскируются до записи.

Запись применённого user-сообщения и переход pending→applied происходят в одной транзакции
add_message; отказ хука помечается rejected. pending сохраняется при отмене, закрытии и
повторном запуске. Экспорт включает pending_inputs, удаление сессии удаляет очередь каскадно.
/revert помечает оставшиеся pending как reverted, чтобы отменённые инструкции не воскресали.

Уточнения сохраняют общий request_id, но получают input_id и checkpoint_id. На безопасной
границе применения закрывается снимок предыдущего сегмента и открывается снимок уточнения.
/revert выбирает checkpoint_id (либо прежний request_id для старых сообщений), поэтому
файловый откат уточнения сохраняет изменения до него. Восстановленное после отмены pending
добавляется до нового запроса и использует начальный снимок свежего цикла: до его применения
в новом цикле модель ещё не запускала действий. Непрерывность файлового отката сохраняется.

По умолчанию CLI использует `$GWAGENT_HOME/sessions.db`: здесь же находятся журнал запросов, вызовы инструментов, метрики, уточнения и снимки отката. `gwagent data migrate` копирует старую базу через SQLite backup с учётом WAL; исходная база сохраняется. На сервере по-прежнему используется DB_PATH шлюза. [Единое хранилище](data.md).

## Схема 7: режим доступа и сводка

Миграция 7 добавляет agent_sessions.permissions_mode (пустая строка — наследовать настройки). Значения default/allow_all/read_only сохраняют выбор текущей сессии отдельно от agent_mode. Версия по-прежнему в agent_meta. Сводка и context_seq обновляются одной транзакцией после сверки отпечатка истории и исходной контрольной точки. Полная история доступна для экспорта и отката.
