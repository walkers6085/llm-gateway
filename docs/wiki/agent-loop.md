# Цикл агента

Код: [`agent/loop.py`](../../agent/loop.py). Тесты: [`tests/test_loop.py`](../../tests/test_loop.py).

`Agent.run(text)` — асинхронный генератор событий. Один запрос пользователя — это цикл:

```
UserPromptSubmit-хук ─▶ сохранить user-сообщение
   ┌──────────────────────────────────────────────────────────────┐
   │ system prompt + вся история сессии ─▶ модель (стрим)          │
   │ сохранить ответ assistant                                     │
   │ нет tool_calls? ─▶ Stop-хук ─▶ done                           │
   │ для каждого вызова по порядку:                                │
   │   разбор и проверка аргументов ─▶ PreToolUse-хук ─▶ права     │
   │   ─▶ (ask ─▶ подтверждение) ─▶ запуск ─▶ PostToolUse-хук      │
   │   ─▶ обрезка ─▶ сохранить tool-сообщение и строку аудита      │
   └──────────── блоки max_steps, проверка повторов после инструментов ──────────┘
```

Вызовы из одного ответа модели выполняются **последовательно** — так проще рассуждать о
правах и побочных эффектах (два `edit_file` одного файла не гоняются наперегонки).

## Создание

```python
agent = Agent(
    llm=LLMClient(http_client),           # см. llm-client.md
    registry=Registry([...]),             # инструменты, см. tools/*.md и mcp.md
    settings=settings,                    # итоговый словарь настроек (settings.md)
    store=SessionStore(db), session=sess, # sessions.md
    hooks=Hooks(settings["hooks"], cwd=sess.workspace, session_id=sess.id),
    approver=async_fn,                    # (запрос) → "allow" | "deny" | "always"
    on_usage=fn,                          # (модель, http-статус, (prompt, completion)) — учёт расхода
)
async for event in agent.run("сделай …"):
    ...
```

Сборку реестра, хуков и MCP по настройкам делает [`agent/runtime.py`](../../agent/runtime.py) — им пользуются и CLI, и сервер.

## События

| `type` | Поля | Когда |
|---|---|---|
| `text` | `text` | кусок ответа модели (стрим) |
| `usage` | `prompt_tokens`, `completion_tokens` | после каждого обращения к модели |
| `step` | `current`, `limit`, `total`, `extended` | перед первым модельным вызовом шага; ретраи не добавляют шаг |
| `assistant` | `content`, `tool_calls` | ответ модели целиком (уже сохранён) |
| `tool_call` | `id`, `name`, `arguments` | вызов принят (аргументы прошли проверку схемы) |
| `permission_request` | `id`, `name`, `arguments`, `subject`, `reason`, `rule` | нужно подтверждение; `rule` — что добавится при «всегда» |
| `tool_result` | `id`, `name`, `ok`, `content`, `decision`, `ms` | результат (уже обрезанный, как его увидит модель) |
| `warning` | `message` | предупреждение хука, ретрай или коррекция повторов — работа продолжается |
| `error` | `message` | ошибка модели, блокировка хуком, лимит шагов или повторный цикл |
| `done` | `reason`: `stop` \| `loop_detected` \| `max_steps` \| `error` \| `blocked` | всегда последнее событие |

`decision` в `tool_result`: `allow`, `deny`, `ask:allow`, `ask:deny`, `error` (вызов не дошёл до прав:
нет инструмента, битые аргументы).

## Системный промпт

Собирается заново на каждом шаге: `system_prompt` из настроек + рабочая папка, дата, ОС +
`additional_context` хуков `SessionStart`. В историю не сохраняется.

## Ошибки и устойчивость

- Ошибка инструмента (`ToolError` или любое исключение) не прерывает цикл: модель получает
  `Ошибка: …` и может исправиться. Неизвестный инструмент, не-JSON аргументы, нарушение схемы —
  тоже ошибки-результаты.
- Ошибка модели (`LLMError`: HTTP-код апстрима/шлюза, обрыв) — событие `error` и `done(error)`.
  Сообщение пользователя остаётся в истории; повторный запрос продолжит с него.
- Результат длиннее `max_tool_output_chars` обрезается посередине: начало (⅔) + конец (⅓) + пометка.
- **Отмена** (`CancelledError` — Ctrl+C в CLI, `/cancel` или разрыв соединения на сервере): для
  вызовов текущего шага, которые не успели выполниться, в историю пишется
  `tool`-сообщение «Отменено пользователем» — история остаётся корректной для продолжения.
- Хук `Stop` с `decision: deny` и `reason` заставляет агента продолжить: `reason` уходит модели
  как новая реплика пользователя. При включённом loop_guard блоки шагов продлеваются; текстовые повторы без инструментов детектором не отслеживаются.

## Подтверждения

`approver` вызывается для каждого `ask`. Ответ ждётся не дольше `permissions.timeout` секунд,
потом — отказ. Нет `approver` — отказ (так работает `gwagent -p` без `--allow-all`).
Ответ `always` добавляет `rule` в `allow_rules` сессии (сохраняется в SQLite), следующие
такие же вызовы в этой сессии проходят без вопроса.

## Надёжность хода и бюджет

Цикл сохраняет начало/исход хода, закрывает вложенные генераторы и восстанавливает незакрытые
пары tool_call/result в finally и при новом запуске. Зарегистрированные секреты маскируются
перед сохранением и выдачей событий. Ошибка length, обрыв SSE или неверная структура не приводят
к выполнению частичных вызовов. Контекст берётся с checkpoint, созданного `/compact` или автосжатием перед шагом.
Сжатие доступно внутри одного длинного хода, сохраняет целые группы tool-call/result,
точный последний пользовательский запрос (включая контекст хука) и выдержку исходной цели.
Текст Stop-хука не заменяет последний настоящий запрос. Summary перечитывается из SQLite
перед каждой сборкой входа. Крупные результаты инструментов при необходимости обрезаются
только в отправляемой копии, с явной пометкой; пользовательский запрос не обрезается.
Ошибки context_length_exceeded/context window и аналогичные допускают один повтор с целью
уменьшить вход вдвое. Повтор разрешён только до первого фрагмента ответа и при фактическом
уменьшении запроса; инструменты повторно не исполняются. Уменьшенный лимит входа
сохраняется до конца текущего хода, чтобы следующие шаги сжимались заранее. Незавершённый вывод не принимается
за ответ. Общий бюджет хода не обнуляется. В трассировке пишется `context.compacted`,
в интерфейс поступает существующее событие warning.
Новые лимиты max_input_tokens, max_output_tokens, max_turn_tokens и model_profiles описаны в
[settings.md](settings.md). Новая причина done — `budget`; типы событий остаются прежними.

## Reasoning, сабагенты и корреляция

`reasoning` — дельта `text` с рассуждениями, которые явно вернул провайдер. Финальное
`assistant` содержит `reasoning_content`; приложение не синтезирует мысли модели.
Все события запуска содержат `request_id` и `span_id`. Один пользовательский запрос
сохраняет общий `request_id` для всех шагов, инструментов и дочерних агентов.
`agent/tracing.py` ведёт контекст через ContextVar; вложенные генераторы закрываются
при отмене с восстановлением контекста. Сообщения связываются с журналом через `message.saved`
с `seq` и ролью; промпты, ответы и reasoning в журнал метаданных не копируются.

Сборка `agent/runtime.py` добавляет `subagent`, если включён `subagents.enabled`.
`subagent_start` сообщает дочернюю `session_id` и задачу; `subagent_event` оборачивает
дочерние события; `subagent_end` содержит причину завершения и итоговый `content`.
`subagent_result` используется только внутри генератора для передачи ToolResult, наружу не отправляется.
Подтверждения и usage дочернего агента идут обычными событиями, чтобы работали существующие
клиенты разрешений и учёт токенов. Дочерняя история отделена от родительской;
владелец, workspace, модель, политика прав и хуки наследуются. Вложенная делегация запрещена.
Бюджет токенов общий; max_calls — на весь пользовательский запрос, размер блока max_steps и timeout — на ребёнка.
Копия LLMClient не меняет настройки родительского клиента. Запуски выполняются последовательно.

Офлайн-проверки: `tests/test_tracing_reasoning.py` — JSON/SSE reasoning, родительские
связи, разрешения ребёнка, лимиты, уникальность ID и отмена с восстановлением обеих историй.

`function` в синтетическом tool_call обозначает тип инструмента, а не отдельное событие цикла.

В ToolContext.extra передаются request_id и span_id текущего вызова; callback разрешений получает те же поля.

## Метрики каждого ответа и снимки хода

`assistant.metrics` содержит `duration_ms` (вызов модели, включая ожидание ответа),
`worked_ms` (прошло с начала пользовательского запроса, включая инструменты),
`completed_at` (ISO 8601 UTC), `completion_tokens`, `tokens_per_second`.
Скорость — completion_tokens / длительность вызова модели; reasoning-токены входят в
completion, если провайдер включает их в usage. Если usage не получен, скорость null,
интерфейс показывает «скорость н/д». Метаданные сохраняются отдельно от OpenAI-истории.
Каждый вызов, включая промежуточные ответы с инструментами и ответы сабагентов, имеет свои метрики.

Корневой `Agent.run` делает снимок workspace до хуков и после окончания/отмены запроса;
дети используют общую workspace и входят в снимок родителя. Снимки не добавляют запросов
к провайдеру. Ошибка/лимит снимка не мешает чату, но делает недоступным файловый откат.
Реализация и ограничения — [сессии](sessions.md).

## Контекст и состояние планирования

Перед каждым вызовом модели (включая ограниченный повтор) событие `context` передаёт
estimated_tokens, max_input_tokens, max_output_tokens, source=estimate и planning
(текущая цель/задачи, включая первый запрос до начала потока). Оно не заменяет
`usage`, который содержит фактический расход, если его вернул провайдер.
При `max_output_tokens: 0` резерв ответа равен нулю: `max_tokens` не отправляется, вход
занимает всё окно модели, а система-промпт просит отвечать кратко.
`Agent.context_status()` строит оценку без запуска сжатия или модели; уменьшенный после
переполнения лимит сохраняется в агенте до следующего пользовательского хода.

`goal` и `todo` — обычные инструменты реестра с проверкой прав и хуками. Успешный результат
сохраняется с metadata.planning; при отказе и ошибке метаданные не записываются.
Состояние восстанавливается из истории и закрепляется во входе после сжатия, см.
[планирование](tools/planning.md). Текст PostToolUse-контекста не подменяет структурированное состояние.

## Два активных агента и уточняющие вопросы

Режим Session.agent_mode (build|plan) фиксируется на время Agent.run, даже если сохранённое
состояние изменилось. system_prompt сообщает роль агента, tool_specs фильтрует инструменты
plan по положительному признаку Tool.plan_safe. Перед запуском инструмента проверка plan
повторяется до PreToolUse: allow_all, правила always и разрешающий хук не включают запрещённый
инструмент. После переключения build использует ту же историю и состояние цели/задач.
Дочерняя сессия наследует режим, а subagent в plan недоступен.

Метаданные сообщений и request.start содержат agent_mode; события цикла также передают
его вместе с request_id. Уточнение реализовано инструментом question и асинхронным callback
questioner, передаваемым Agent/make_agent. Цикл ждёт его результат внутри обычного инструмента;
не запускает второй модельный запрос до ответа. Вопросы имеют question.start/end в трассировке,
отмена сохраняет обычный инвариант пар вызова/результата. [Подробности](tools/question.md).

## Уточнения в текущем цикле

Agent.steer(text, input_id=...) принимает сообщение только при running_request_id и
сохраняет его через SessionStore.enqueue_input. Интерфейс может сделать это и во время
сборки LLM-клиента, зная App.active_request_id. Не создаётся новый turn/request_id,
не сбрасываются бюджет, счётчики шагов и активный режим; детектор повторов сбрасывается. Каждый уточняющий ввод имеет input_id;
model.start и метаданные сообщений связывают его с корневым request_id.

Очередь FIFO обрабатывается перед вызовом модели и перед финальным done. Каждый текст
проходит UserPromptSubmit с steering=true/input_id и получает его additional_context.
`input_applied` подтверждает включение в историю, `input_rejected` — отказ хука.
Результат первого события не обещает дополнительный вызов сверх заданного бюджета расхода;
при исчерпании лимита текст уже сохранён для продолжения.

Если уточнение поступило при выполнении инструмента, текущий инструмент завершается.
Оставшиеся вызовы пачки получают tool-результат decision=steering:skip и не исполняются;
после закрытия всей группы добавляется user-сообщение. Так не возникает user между
assistant.tool_calls и обязательными tool-результатами. Модель пересматривает действия
с новым контекстом. При потоковом ответе сообщение подмешивается после завершения текущего
вызова; уже выданные фрагменты/частичные вызовы не обрываются и не переисполняются.
После прямой делегации /agent уточнение продолжает родительский цикл после результата ребёнка.

Отмена/ошибка оставляет неприменённые сообщения в SQLite. При следующем запросе в этой
сессии старые сообщения сначала проходят хук и добавляются до нового пользовательского
запроса: свежий запрос остаётся последним. Чужие сессии и дочерние циклы их не забирают.
Журнал input.queued/applied/rejected содержит идентификаторы, без содержимого текста.


Для модели с tools=false (профиль, параметры подключения или общие настройки) tool_specs
не объявляет схемы инструментов, поэтому модели без tool calling могут отвечать текстом.
Профили провайдеров задают отдельные лимиты входа/выхода и параметры запроса; переключение
подключения не переносит их в другой провайдер. [Настройки](settings.md).

Временная ошибка, включая сетевой обрыв после текста/reasoning, повторяется с backoff в том же шаге, с новым model-span и прежним request_id. `warning` может содержать `retry`: attempt/max_retries/delay/status. Ожидание отменяемо и принимает уточнения перед повтором; инструменты не переигрываются, бюджет не сбрасывается. Копия tool-истории проходит context_cleanup до оценки размера, исходная SQLite-история не меняется. Журнал model.retry/context.cleaned не содержит текста запросов. [Подробности](request-processing.md).

Сжатие теперь вызывается асинхронно: текущая модель составляет сводку без инструментов; при ошибке/лимите применяется локальное сжатие. Подробности — [обработка запросов](request-processing.md). Режим read_only фильтрует доступные модели инструменты и проверяется повторно до PreToolUse; allow/always не снимают запрет.

`context` и context_status дополнительно сообщают context_window/context_source/context_known/input_limit_source. Лимиты для каждого запроса, бюджета и сводки вычисляет общий model_limits.resolve. По умолчанию max_input_tokens=0 включает автоопределение окна, а max_turn_tokens=0 отключает общий бюджет хода. Явный положительный бюджет ограничивает суммарный расход, включая сводки и сабагентов; сжатие его не сбрасывает. Оценка размера — байты JSON / 3 с округлением вверх плюс 64, не точный токенизатор.

Ручной `/compact` всегда запрашивает сводку текущей модели и оставляет прежний контекст при ошибке; результат доступен в Agent.last_compaction (method и причина reason при сбое). Автоматическая подготовка контекста повторяет суммаризацию доступных частей, пока контекст не помещается или сжимать больше нечего; затем при необходимости ограничивает отправляемые tool-результаты. Временные ошибки суммаризации повторяются с учётом таймаута и бюджета.

Повторы во время автоматической подготовки контекста передаются через _context_progress: при необходимости сжатия подготовка работает в дочерней asyncio-задаче с общей корреляцией и бюджетом, warning.retry выдаётся до ожидания backoff. Закрытие генератора отменяет задачу подготовки и дожидается её завершения. Agent.compact(on_progress=...) позволяет ручной команде передавать тот же статус.

Автоматическое название сессии выбирается SessionStore.ensure_title из исходных
пользовательских запросов, с пропуском приветствий и коротких продолжений. Ручное
название сохраняется. В ToolContext.extra.statistics доступна функция агрегатов
только текущей сессии и её владельца; инструмент statistics не обращается к модели.

## Исследование перед планом и внутренние роли

Plan получает инструкции самостоятельно проверить доступные факты до финального плана,
назвать результаты, конкретные изменения и критерии готовности. Непроверенные факты и
блокировки выделяются явно; неизвестные предпочтения выясняются через question.
Инструмент inspect проверяет наличие программы/пути или HTTP HEAD без shell.

Subagent принимает role=explorer|reviewer|worker и необязательный context. В Plan/read_only
роли и схема ограничены explorer/reviewer; проверка аргументов повторяется после хука.
Их ребёнок всегда работает в Plan с отфильтрованным реестром инструментов, сохраняя
защиту файлов учётных данных и контекст инструментов родителя. Промпты ролей задают сбор
проверяемых фактов и независимое ревью; worker сохраняет поведение исполнителя Build.
Родитель рекомендует делегирование существенных исследований/проверок, а не всех ответов.
Событие журнала session.internal с ролью маркирует внутреннюю сессию. События
subagent_start/end содержат role, start также hidden; отмена, timeout, учёт usage,
request_id и инвариант tool_call/result сохраняются. Вложенные роли запрещены.

Родительский системный промпт сообщает реальный остаток max_calls на текущий запрос,
размер блока шагов и таймаут ребёнка. После исчерпания слотов проверки выполняет сам родитель.

Plan после готового плана явно предлагает перейти в Build (Tab в TUI, /mode build
в CLI) либо прислать уточнение. При существенном выборе используется question до
завершения плана. Build также задаёт вопросы при нехватке требований. Смена режима
и начало реализации автоматически из ответа модели не выполняются.

warning.retry.reset_response=true отбрасывает незавершённые текст и reasoning перед
повтором текущего запроса модели. error.reset_response=true очищает их при исчерпании
повторов временного сбоя. Обработанные инструменты не переигрываются, частичные tool_calls
не исполняются. Окно model_retry.max_elapsed основного цикла отсчитывается от первой ошибки.


## Защита от зацикливания и блоки шагов

Код: [`agent/loop_guard.py`](../../agent/loop_guard.py), проверки:
[`tests/test_loop_guard.py`](../../tests/test_loop_guard.py).
Детектор хранит последние 24 SHA-256 сигнатуры: имя инструмента, эффективные аргументы
после PreToolUse, признак ошибки, результат после PostToolUse/редактирования секретов/обрезки.
JSON-ключи сортируются; порядок массивов, строки команд и значения сохраняются.
Проверяются хвостовые последовательности длиной 1–4, повторившиеся трижды подряд.
Ошибки, отказы и MCP учитываются наравне с остальными результатами; пропущенные вызовы
и сетевые ретраи не учитываются. Меняющийся результат разрывает повтор.

Первое обнаружение дополняет tool-результат инструкцией сменить подход или объяснить
препятствие, выдаёт warning и очищает окно наблюдений. Остаток пакета получает
`decision=loop_guard:skip` без запуска и запроса разрешений. Повторное обнаружение после
коррекции завершает запрос с `done.reason=loop_detected`; сессия доступна для продолжения.
Для каждого tool_call_id сохраняется tool-ответ, включая пропуски. Изменения файлов не откатываются.

По умолчанию max_steps=25 — размер блока, а не общий потолок. После 25 обращений к
модели следующий шаг имеет current=1, total=26; затем 1/51 и так далее. Детектор
проверяет каждый результат и не сбрасывается на границе блока или при compact.
Сетевые ретраи и служебная суммаризация не добавляют шагов. Событие `step` содержит
`current`, `limit`, `total`, `extended`; extended=true только на первом шаге нового блока.
При отключённом loop_guard действует прежний жёсткий max_steps и done.reason=max_steps.
Отмена, бюджеты токенов и таймауты не продлеваются. Каждый сабагент имеет собственный
детектор и блок, ограниченный минимумом max_steps родителя и subagents.max_steps;
общий расход и лимит числа делегаций сохраняются.

Новый запрос и применённое уточнение сбрасывают окно и использованную коррекцию.
Отклонённое уточнение ничего не сбрасывает. Отсутствие срабатывания не гарантирует
прогресс: изменяющиеся временные метки и текстовые ответы без инструментов могут
скрывать цикл. Точный анализ reasoning и общий таймаут основного запроса не добавлены.

Журнал: `loop_guard.detected`, `loop_guard.corrected`, `loop_guard.stopped` содержат
длину паттерна, число повторов и действие; `loop_guard.extended` — общий счётчик
завершённых шагов и размер блока. Все записи используют текущие request_id/span_id,
новые записи не содержат аргументов, текста результатов или их хешей.
